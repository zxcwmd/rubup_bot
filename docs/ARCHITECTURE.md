# Архитектура

## 1. Компоненты

```text
                         ┌──────────────────────────┐
Telegram user ──────────▶│ telegram.py (aiogram)   │
                         │ buttons, ACL, reports   │
                         └────────────┬─────────────┘
                                      │
                         ┌────────────▼─────────────┐
                         │ service.py               │
                         │ scheduler + orchestrator │
                         └───────┬────────┬─────────┘
                                 │        │
             ┌───────────────────▼─┐    ┌─▼───────────────────┐
             │ rules.py / text.py  │    │ tiktok.py           │
             │ eligibility + text  │    │ one Playwright      │
             └─────────────────────┘    │ persistent profile  │
                                        └──────────┬──────────┘
             ┌─────────────────────┐               │
             │ images.py           │        TikTok website
             │ immutable library   │
             └──────────┬──────────┘
                        │
             ┌──────────▼──────────┐
             │ db.py / SQLite      │
             │ invariants, history │
             └─────────────────────┘
```

- **`telegram.py`** — только интерфейс и Telegram ACL. Не содержит правил публикации.
- **`service.py`** — единственная точка оркестрации. Сериализует браузерные операции через `asyncio.Lock`.
- **`tiktok.py`** — сменный адаптер внешней площадки. Навигация, метаданные, чтение комментариев, одна попытка публикации.
- **`rules.py`** — чистые проверки даты, своего автора, маркеров и похожих исходных комментариев.
- **`text.py`** — шаблоны, тематический контекст, рекламная пометка и текстовая схожесть.
- **`images.py`** — проверка формата, SHA-256, импорт неизменяемых копий.
- **`db.py`** — транзакции, уникальные ограничения, состояния и отчёты.

## 2. Цикл автоматизации

1. Проверить `auto_enabled` в SQLite.
2. Импортировать новые изображения и вернуть в очередь видео, ожидавшие картинки.
3. Проверить сессию в единственном persistent browser profile.
4. Взять следующую группу тегов по кольцевому курсору.
5. Собрать канонические ссылки на видео; удалить query/tracking-параметры.
6. Открыть только новые видео, извлечь описание, автора и `createTime` из встроенного JSON.
7. Оставить только разрешённые теги и дату не раньше `MIN_VIDEO_DATE`.
8. Продолжить безопасные `pending`-действия, прерванные **до** нажатия публикации.
9. Для новых видео прочитать комментарии:
   - обработать подходящие чужие RubUP-комментарии;
   - исключить свои, обработанные и похожие;
   - создать основной комментарий только при наличии новой картинки.
10. Проверить публикацию в DOM. Неопределённый результат передать человеку.
11. Записать событие и отправить уведомление администратору.
12. Подождать заданный интервал или событие пробуждения.

Поиск по кнопке выполняет только шаги 3–7. Публикация из этого обработчика не вызывается.

## 3. Инварианты на уровне SQLite

Прикладных проверок недостаточно, поэтому важные правила закреплены в схеме:

- `actions.dedupe_key UNIQUE`:
  - основной комментарий: `comment:<video_id>`;
  - ответ: `reply:<video_id>:<target_comment_id>`.
- Частичный уникальный индекс `actions.normalized_text` не даёт повторно использовать нормализованный текст.
- `images.sha256 UNIQUE` исключает одинаковое содержимое.
- Выбор изображения и создание действия выполняются в `BEGIN IMMEDIATE`; статус меняется только с `available` на `reserved`.
- `reports` и `actions.report_id` связывают ссылку с одним отправленным отчётом.
- Один аккаунт не требует account_id в ключах: архитектура намеренно однопользовательская и имеет один профиль.

## 4. Состояния действия

```text
pending ──▶ publishing ──▶ published
   ▲            │
   │            ├────────▶ manual_review ──▶ published (подтвердил человек)
   │            │                    └─────▶ failed (публикации нет)
   │            │
   │            └────────▶ failed
   │                         │
   └──── /retry только если ◀┘
        публикации точно нет
```

- `pending` после проверки безопасности разрешён только когда адаптер не сообщил о нажатии публикации.
- После попытки нажатия любые неопределённые ошибки переводятся в `manual_review`, а не автоматически повторяются.
- `/retry` не создаёт новый текст и не берёт новую картинку: повторяется та же запись после явного решения администратора.

### Состояния видео

- `queued` — можно обрабатывать;
- `skipped` — не подходит по дате/тегу;
- `waiting_images` — ответы обработаны, но основной комментарий ждёт новую картинку;
- `processed` — основной комментарий опубликован или уже существует;
- `attention` — нужна ручная проверка или исправление адаптера.

### Состояния изображения

- `available` — никогда не выбиралось;
- `reserved` — связано с действием, не выдаётся другому видео;
- `used` — публикация подтверждена.

## 5. Отчётность

При нажатии «Отправить отчет»:

1. В транзакции создаётся `pending` report и связывается со всеми ещё не отчитанными `published` действиями.
2. Повторное нажатие до завершения использует тот же report, а не собирает другой набор.
3. Telegram получает только строки URL. Несколько оплачиваемых действий на одном видео дают несколько строк.
4. После успешной отправки всех частей report становится `sent`.

Между внешней отправкой и фиксацией `sent` невозможна строгая распределённая транзакция. Поэтому после сбоя связи пользователь должен проверить чат: система выбирает безопасный повтор pending-отчёта.

## 6. Конкурентность и надёжность

- Один event loop, один scheduler, один browser context и одна блокировка браузерных операций.
- Telegram-операции поиска/проверки сессии запускаются как отслеживаемые фоновые задачи.
- SQLite WAL и `busy_timeout` уменьшают конфликты коротких записей.
- Не поддерживается запуск нескольких процессов над одной базой/профилем.
- Ожидаемые внешние сбои не удаляют историю и не освобождают одноразовую картинку автоматически.

## 7. Точки расширения

- Новая версия интерфейса TikTok: преимущественно `selectors.json`, при изменении JSON-структуры — `tiktok.py`.
- Другой генератор текста: реализовать тот же интерфейс `CommentGenerator.generate`, сохранив фильтры и disclosure.
- Другой источник видео: добавить discovery-adapter, который выдаёт канонические URL и проходит общие правила.
- Дополнительный признак RubUP: расширить `CommentRules`, сохранив исключение своего автора и dedupe key.

Мультиаккаунтность нельзя добавлять простым запуском копий с общей БД: потребуется отдельная модель аккаунтов, профилей, ключей идемпотентности и лимитов.

## 8. Тестовая стратегия

- Чистые unit-тесты правил, URL, времени, нормализации и сходства.
- Интеграционные тесты SQLite на временных файлах.
- Импорт реальных миниатюр PNG через Pillow, дубликаты и повреждённые файлы.
- Сквозной сценарий с fake TikTok: чужой ответ + основной комментарий + картинка + отчёт.
- Конструирование aiogram UI в тесте проверяет регистрацию handlers/middleware без сетевых вызовов.

Live-публикация намеренно не входит в автоматические тесты.
